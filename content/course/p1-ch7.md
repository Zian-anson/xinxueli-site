## 本课目标

把前六章的改造收拢成一个属于你自己的 Harness：从原项目 fork 出来，起自己的名字，组自己的 profile，装自己的 patch 和插件。并且做到：换一台机器，照你自己的说明能重建。

## 正文

### 什么是「自己的 Harness」

不是从零写一个新项目，也不是在原安装里随手改几处。它是：

- 一份你自己的版本，和原项目分开放；
- 一个你自己起的名字；
- 一份你自己的 profile，决定装哪些组合；
- 一组你自己的 patch 和插件，决定它和默认版哪里不一样。

标准只有一条：**换台机器，照你的 README 能重建出来。** 做不到，它就只是你电脑上的一堆临时改动。

### 第一步：fork 出自己的版本

Fork 是复制一份你可以改的版本，同时保留和原项目的关系，方便以后同步更新。

让 AI 做四件事：

1. 把当前项目 fork 到你的目录，放在原安装之外；
2. 保留上游仓库地址；
3. 给你一份后续同步上游改动的步骤；
4. 确认 fork 出来的版本能独立构建和启动。

不要在原始安装目录里改。原安装是别人发给你的一份成品，改了以后升级会冲突；你的版本要能自己走路。

### 第二步：起名字、定 profile

名字是你自己的，写在 README 和配置里。它不重要，但它标记「这是我的」。

profile 重要得多：它决定这棵树叠哪些组合包。做法：

1. 从你每天真实在用的设置出发；
2. 去掉你从来不用的插件；
3. 加上你每天都要用的；
4. 每加一个，问一句：它解决我什么问题？答不上来就去掉。

目标不是「插件越多越好」，是「这套组合贴合我的工作方式」。

### 第三步：装上你的 patch 和插件

把第 6 章的成果搬进你的 fork：

- 配置文件；
- patch 文件；
- 插件文件；
- 启用方式。

然后做一次干净启动：全部关掉，打开你的 Harness，发一条消息，调用一次你的插件，打开一个会话。四样都过，再继续。

搬的过程中最容易漏的是「启用」。文件在，没启用，等于没装。每搬一样，验收一样。

### 第四步：让它可持续

三件事：

1. **README**：写清这是什么、怎么装、怎么启用、怎么卸载、依赖什么版本。
2. **changelog**：每次改动记一行——改了什么、为什么、怎么回退。
3. **上游同步路**：保留上游地址和同步步骤。DSH 还在开发者预览，迭代快；不要追每个更新，需要修 bug 或要新功能时再同步。

不要把所有改动堆在一个补丁里。按功能拆开，出问题好定位，也好分享给别人。

### 毕业验收

对着下面五条打勾：

- 我能说清哪些部分是我自己的，它们各干什么；
- 我能把任意一项撤掉，应用还能正常跑；
- 我在干净环境里，照自己的 README 重建成功过一次；
- 我用它做过一件真实的事，不是只跑了个 demo；
- 我知道怎么同步上游，不会一升级就全坏。

五条全过，开发主线毕业。

## 要点卡

- 自造 Harness = fork + 名字 + profile + 自己的 patch/插件
- 不在原安装里改，保持自己的版本可独立构建
- 标准是「换台机器能按你的 README 重建」
- README、changelog、上游同步路，三样都要有
- 插件不是越多越好，贴合自己的工作方式才好

## 动手练习

完成你的 Harness：

1. fork 出独立版本，保留上游；
2. 起名字，写 profile；
3. 装入至少一个 patch 和一个插件；
4. 写 README 和 changelog；
5. 在干净环境按 README 重建一次，记录卡住的地方。
